# Security baseline

Every homelab server gets the same hardened starting point from six Ansible roles: `base` (`roles/base/`) hardens the operating system, `docker` (`roles/docker/`) installs Docker Engine, `dns_host` (`roles/dns_host/`) prepares the host for the DNS stack, `portainer` (`roles/portainer/`) runs Portainer CE, `portainer_stacks` (`roles/portainer_stacks/`) sets Portainer up through its API, and `backup` (`roles/backup/`) archives the Docker volumes that hold state every night. Portainer then deploys the app stacks from `stacks/` in this repo: the DNS stack (Pi-hole + Unbound) and the proxy stack (Nginx Proxy Manager, with certificates from a private CA built by `playbooks/pki.yml`). This page lists each control, where it lives in the code, how to check it on a running server, and the Security+ concept it maps to.

**Applies to:** the test VM `test-homelab` today, and the production ThinkPad from Week 10. **Last verified:** 26 Nov 2026, in a disaster-recovery drill that rebuilt the test VM from a fresh install and restored its data ([Week 9 build log](build-log/week-09.md)).

## Docker bypasses UFW

**Finding (18 Nov 2026):** a container started with `docker run -d --name trap -p 8080:80 nginx` was reachable from another machine at `http://192.168.77.50:8080`, while `ufw status` still showed deny incoming with only `22/tcp` allowed.

**Why:** a published port is handled by Docker's own iptables rules, not by UFW.

1. Docker adds a `nat` rule for each published port: `-A DOCKER ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80`. It rewrites the destination to the container's internal address before the kernel decides where the packet goes.
2. The packet is no longer addressed to the server itself, so it goes through the **FORWARD** chain, not **INPUT**. UFW's "deny incoming" rules live in INPUT and never see it.
3. In FORWARD, Docker's chains come first (`-A FORWARD -j DOCKER-USER`, then `DOCKER-FORWARD`), and `-A DOCKER -d 172.17.0.2/32 … --dport 80 -j ACCEPT` accepts the packet before UFW's "deny (routed)" rules are reached.

**Fix tested:** with `-p 127.0.0.1:8080:80` the port is published on the loopback address only. From the LAN, `curl -m 5 http://192.168.77.50:8080` timed out; on the server, `curl http://127.0.0.1:8080` still returned the nginx page.

**Rules for every container from Week 5 on:**

| Kind of port | Rule | Firewall that applies |
| --- | --- | --- |
| Only used on the server, or only reached through the reverse proxy | Publish on `127.0.0.1` (`127.0.0.1:<host>:<container>`), or don't publish it at all and use a Docker network. | None needed: not reachable from the LAN |
| Must be reachable from the LAN (Nginx Proxy Manager 80/443 since Week 7; Portainer 9443 in Weeks 5–6) | Publish deliberately and list it in the table below. UFW does **not** protect it. If it must be limited by source address, the rule goes in the `DOCKER-USER` chain, which Docker never changes and checks first. | Docker's iptables rules (UFW is bypassed) |
| Container on the host network (Pi-hole) | Behaves like a normal host service. | UFW, through the rules the `dns_host` role adds |

**Ports published to the LAN:**

| Port | Container | Published as | Why it's LAN-facing | Source filter | Until |
| --- | --- | --- | --- | --- | --- |
| `80/tcp`, `443/tcp` | `npm` (Nginx Proxy Manager) | `0.0.0.0:80`, `0.0.0.0:443`, and `[::]:80`, `[::]:443` (Docker publishes on IPv6 too) | The front door for every admin UI. Port 80 only redirects to HTTPS. | None. Every proxy host behind it has its own login. | Permanent |
| `53/tcp`, `53/udp` | `pihole` (DNS) | Host network; UFW rule from `dns_host` | DNS for the LAN is Pi-hole's whole job. | UFW allows any source. Pi-hole itself only answers devices on local subnets (its default listening mode). | Permanent |

No longer LAN-facing since Week 7: Portainer's `9443` isn't published at all, and Pi-hole's `8081` is allowed by UFW only from the `proxy` network (`172.20.0.0/24`). NPM's admin port `81` and Unbound's `5335` are published on `127.0.0.1` only. On the test VM, DHCP's `67/udp` is closed; in production it opens when `dns_host_dhcp_active` is true.

**How to check:** `docker ps` shows each container's published address in the PORTS column (`127.0.0.1:8080->80/tcp` is local only; `0.0.0.0:8080->80/tcp` is open to the LAN). `sudo iptables -t nat -S DOCKER` lists every DNAT rule.

**Not chosen:** turning off Docker's iptables management (`"iptables": false` in `daemon.json`) breaks container networking and needs hand-written NAT rules. Third-party scripts that rewrite UFW's rules for Docker add something else to maintain. Binding to `127.0.0.1` plus a short, documented list of LAN-facing ports needs neither.

## Decisions and accepted risks

| Decision | Why | Risk accepted, and what limits it |
| --- | --- | --- |
| Keep `50-cloud-init.conf` (it sets `PasswordAuthentication yes`) | Our `10-hardening.conf` is read first and wins, so the hardening doesn't depend on cloud-init never rewriting its file. | None while the `10-` prefix stays lower than `50-`. `sshd -T` shows the effective value. |
| No `AllowUsers` yet | One wrong username there locks everyone out, and key-only login with no root already closes the main paths. | Any account with an authorized key can log in. Revisit once the user list is settled. |
| No passwordless sudo; the become password lives in Ansible Vault | A stolen SSH key alone shouldn't give root. Vault removes typing `-K` without removing the password. | The SSH key and the vault password file are both on the control node, so someone who takes over my WSL account gets root on the server. The control node is part of the trust boundary. |
| Vault password rotation documented, not yet run | The password is random and has never left the control node and the password manager. | Rotate it if it may have leaked, a device holding it is lost, or someone who knew it no longer should. Steps in [ADR 0002](adr/0002-secrets-with-ansible-vault.md). |
| The admin user is in the `docker` group | Day-to-day `docker` commands work without `sudo`. | Members of the `docker` group are effectively root: they can start a container that mounts `/` from the host. Only the admin user is in `docker_users`. |
| Automatic reboots on, at 04:00 | A kernel or library fix doesn't protect the server until it reboots. Upgrades run between about 06:00 and 07:00, so the reboot lands at 04:00 the next morning, when nobody is using the network. | From Week 10 this server is the home's only DNS and DHCP server: a reboot is a short outage, and a failed boot is a full one. Fallback: the Pi-hole-down runbook (turn DHCP back on at the BGW320). A fix that needs a reboot can wait up to about a day. |
| Portainer mounts the Docker socket (`/var/run/docker.sock`) | Portainer manages Docker through the socket; without it there's nothing to manage. | Anyone who is a Portainer admin, or who exploits a Portainer vulnerability, is effectively root on the host: they can start a privileged container that mounts `/`. Limits: a strong admin password, a pinned and patched LTS release, and the UI reachable only from the LAN, through NPM. Mounting the socket read-only (`:ro`) wouldn't help, because it doesn't stop API calls through the socket. |
| NPM's 80 and 443 are published to the LAN without a source filter | They're the way in to every admin UI, and the home network is one flat subnet, so a filter would only exclude the few devices that aren't the desktop. A `DOCKER-USER` rule would also need a DHCP reservation for the desktop. | Any device on the LAN can reach the login pages of NPM, Pi-hole and Portainer, over HTTPS. Each has its own strong password. Revisit if the network is segmented later (not part of v2). |
| NPM's admin UI has a proxy host (`npm.home.arpa`) | Managing proxy hosts through an SSH tunnel every time is slow, and the UI is behind the same HTTPS and login as the others. | NPM's login page is reachable from the LAN, not only through a tunnel. An NPM admin can point a name anywhere and read the uploaded server key. Strong password in Bitwarden; port 81 itself stays on loopback. |
| NPM doesn't check the certificates of the services behind it | Portainer keeps its own self-signed certificate on 9443, and Pi-hole is plain HTTP on 8081. NPM terminates the browser's TLS with the private CA's certificate. | The hop from NPM to Portainer or Pi-hole isn't authenticated or (for Pi-hole) encrypted. It never leaves the server: it runs over the `proxy` bridge, and 8081 is allowed only from that subnet. |
| Stay on Portainer CE, frozen on the 2.45 LTS line | Portainer announced in September 2026 that there will be no CE build of 3.x; 2.45 LTS still gets security and bug fixes. See [ADR 0003](adr/0003-ansible-owns-host-portainer-owns-apps.md). | If CE fixes stop, Portainer becomes unpatched software with root-level access. The stacks are plain Compose files in Git, so they can move to another manager without rewriting the apps. |
| Only the security pocket updates automatically | That's Ubuntu's default: security fixes are small and targeted. | Non-security updates wait for the next `site.yml` run, whose upgrade task applies everything. |
| Pi-hole's firewall rules come from the `dns_host` role, not `base_ufw_allowed` | The DHCP port has to follow a variable and be removed again when it's off, and the ports belong with the service that needs them. | Firewall rules now come from two roles. Both are listed in this baseline, and `sudo ufw status` shows the full result. |
| The server uses the network's DNS, not its own Pi-hole | If the server depended on its own Pi-hole, a stopped container would leave Docker unable to pull the image that fixes it. | The server's own lookups aren't filtered by Pi-hole. On the test VM they go to the production Pi-hole; in production, netplan sets them in Week 10. |
| Pi-hole's admin password is a Portainer stack environment variable | It has to reach the container without being written in the public repo. `portainer_stacks` sends it from Ansible Vault through Portainer's API when it creates the `dns` stack. | Any Portainer admin can read it on the stack page, and anyone in the `docker` group can read it with `docker inspect pihole`. Both already mean root on the host. |
| Portainer's setup token stays in its container's environment | `PORTAINER_SETUP_TOKEN` has to be set when the container is created, before any admin exists ([ADR 0006](adr/0006-portainer-admin-setup-token.md)). | Anyone who can run `docker inspect portainer` can read it: root or the `docker` group, who already control the host. Portainer ignores it once an admin exists, so it only matters during the first seconds of a fresh install. |
| The API calls skip certificate checks (`validate_certs: false`) | `portainer_stacks` talks to the container's own address, where Portainer serves a self-signed certificate. NPM isn't set up yet on a fresh server, so the private CA's certificate isn't in that path. | The calls aren't protected against a man in the middle, but they never leave the server: Ansible runs them on the host against the `proxy` bridge. |
| `NET_ADMIN` is granted to Pi-hole on the test VM too | The same compose file runs in production, where DHCP needs it; the test VM only differs by a variable. | Pi-hole runs with more network privileges than it uses on the test VM. Its DHCP server stays off and locked, and 67/udp is closed. |
| Portainer polls `main` and redeploys automatically | Git is the source of truth (ADR 0003); a push should be all it takes to change the server. | Whoever can push to `main` changes what runs on the server, so the GitHub account (with 2FA) is part of the trust boundary. Every push that changes a service restarts it: a restarted Unbound means a few seconds without DNS. A manual **Pull and redeploy** restarted both `pihole` and `unbound`, not only the changed one. |
| A private CA instead of public certificates | `home.arpa` can't get certificates from a public CA. A real domain with Let's Encrypt would need a DNS provider token on the server ([ADR 0005](adr/0005-private-ca.md)). | Only devices that import `ca.crt` trust it; today that's the desktop. No revocation (no CRL or OCSP): a leaked server key stays valid until the certificate expires (23 Dec 2027 at the latest), and a leaked CA key is limited by its `home.arpa` name constraint until it's removed from the desktop. Renewal is manual. |
| The CA key lives on the control node and in Bitwarden | A key that's never on a server can't be stolen from one, and the Bitwarden copy survives losing WSL. | Someone who takes over my WSL account and the vault password can sign `home.arpa` certificates the desktop trusts. The same trust boundary as the SSH key and vault password. |
| HSTS is off on every proxy host | HSTS makes browsers refuse plain HTTP to a name for months, which would lock out the UIs if the CA were ever rebuilt or a certificate broke. | A first visit typed as `http://` is redirected rather than refused, so it could be intercepted on the LAN before the redirect. Force SSL still upgrades every request. |
| NPM's proxy hosts and uploaded certificate aren't in Git | NPM keeps them in its own database in the `npm_data` volume ([ADR 0005](adr/0005-private-ca.md)). | A rebuild from code doesn't bring them back without a restore. They're listed in ADR 0005 and the Week 7 build log, and in the nightly backup since Week 9; the DR drill restored them with their original creation dates. |
| About 6 seconds without DNS every night at 02:30 | Stopping Pi-hole, NPM and Portainer lets their SQLite databases be copied in a consistent state. A live copy can catch a database mid-write and give an archive that won't restore ([ADR 0008](adr/0008-backups.md)). | Lookups fail for a few seconds at 02:30. Devices retry, and the time is chosen for when nobody uses the network. |
| Backups aren't encrypted at rest | They're root-only on the server and in a `0700` folder on the control node, and both machines are already in the trust boundary (they hold the SSH key, the vault password and the CA key). | Anyone who gets root on the server, or my WSL account, can read Pi-hole's password hash and the server certificate's key from them. That's the same access those machines already give. Nothing goes off-site until it's encrypted. |
| Unbound comes from a third-party image with one maintainer | NLnet Labs publishes no official image; klutchell's was the only one on the 1.26.2 security release ([ADR 0004](adr/0004-unbound-image.md)). | Updates depend on one person. Pinned by digest, so nothing changes without a commit. If releases lag, switch to `madnuttah/unbound`. |

## Known gaps

- **LAN-facing container ports aren't filtered by source.** NPM's 80 and 443 are open to every device on the LAN, because UFW doesn't apply to published ports. `DOCKER-USER` rules can close this if needed; decided per port.
- **`portainer_stacks` only creates; it never updates.** A changed password or `HOMELAB_IP` in Vault or `vars.yml` doesn't reach a stack that already exists; it has to be changed in Portainer too (or the stack deleted and re-created). Updating with a `PUT` is a stretch goal. Changing the Portainer admin password in Vault doesn't change the account either.
- **NPM's configuration is clicked, not coded.** The three proxy hosts and the custom certificate live in NPM's database ([ADR 0005](adr/0005-private-ca.md)). The nightly backup makes them recoverable, but they still aren't reviewed in Git. The certificate also has to be re-uploaded by hand when `pki.yml` renews it, before 23 Dec 2027.
- **Only the desktop resolves the `home.arpa` names, through its hosts file.** Production's Pi-hole gets the records from `HOMELAB_IP` in Week 10; until then the desktop has a hosts-file line pointing them at the test VM.
- **The manual Portainer first-run through an SSH tunnel is written down but untested.** It's only a fallback now that `portainer_stacks` creates the admin.
- **A changed Unbound config isn't applied automatically.** Ansible updates `/opt/homelab/unbound/pi-hole.conf`, but Unbound only reads it when it starts, so the container has to be restarted from Portainer.
- **A Docker restart still closes published ports for under a second.** Live restore keeps the containers running, but Docker 29 replaces the `docker-proxy` processes, so Unbound's `127.0.0.1:5335` and NPM's 80, 443 and 81 close briefly. Pi-hole keeps answering on port 53, but a lookup it forwards to Unbound in that moment fails. Docker restarts are rare (a `daemon.json` change or a manual Docker upgrade), and clients retry. If it ever matters: `"userland-proxy": false`, or Pi-hole forwarding to Unbound over the Docker network instead of the published port.
- **No healthchecks on the DNS containers.** `depends_on` only orders the start-up, so right after a boot Pi-hole can send queries before Unbound is ready, and the first lookups on an empty cache can time out.
- **The `pre-commit` hook only protects clones where it's turned on.** `core.hooksPath` is a local setting, so a fresh clone has no hook until `git config core.hooksPath scripts/hooks` is run. GitHub push protection is the second layer.
- **Removing a port from `base_ufw_allowed` or `dns_host_ufw_allowed` doesn't close it.** Ansible only adds UFW rules; closing one needs `delete: true`. `dns_host` supports it per entry (the old open 8081 rule uses it); `base_ufw_allowed` doesn't yet.
- **SSH is reachable from the whole LAN.** No source restriction yet, and the home network is one flat subnet. Segmentation is out of scope for v2.
- **No off-site backup.** The archives exist on the server and on the control node. On the test VM both are on the desktop's SSD; in production they're two devices in one house. An off-site copy (the last "1" of 3-2-1) needs encryption first.
- **The private CA isn't in any backup.** `~/.homelab-pki/` lives only on the control node; only the CA key and its passphrase are in Bitwarden. A restore doesn't need it (the server certificate is in `proxy_npm_data`), but a new certificate does.
- **The backup helper image is pinned by tag only** (`alpine:3.24.4`), not by digest.
- **No intrusion detection or central logging yet.** UFW logs blocked traffic locally (`Logging: on (low)`). Suricata left v2 with the segmentation lab; Wazuh is paused until after v2.x.
